# Overview: Workflow Control Layer — нюансная документация прототипа

> Источники: `01_tz.md`, `02_architecture.md`, `03_roadmap.md` (присланы как готовое ТЗ/архитектура/roadmap), Alliance Deck (Stanislavsky × ClickUp, 2026).
> Этот документ **не дублирует** исходники, а (1) сводит их в единую модель, (2) явно проговаривает то, что в исходниках подразумевается, но не зафиксировано, (3) фиксирует допущения по местам, где решение ещё не принято.

## 1. Что мы строим одной фразой

Прокладка между двумя источниками истины, которая **транслирует** факты производства (Stanislavsky → ClickUp) и **маршрутизирует** решения человека обратно (ClickUp → Stanislavsky), не давая двум системам разойтись — за счёт того, что у каждой сущности ровно один хозяин, а не за счёт синхронизации.

Это не таск-трекер и не agent-framework. Это **контрактный слой** между ними: три контракта (событие агента, фильтр видимости, роутер обратного канала) — и всё остальное (доска, дешборды, статусы) — бесплатное следствие штатных возможностей ClickUp.

## 2. Кто есть кто (роли из деки, не из ТЗ — но важны для контекста)

Deck вводит "труппу" из 7 ролей, которых нет в ТЗ явно, но именно они — источники AgentEvent в реальной системе:

| Роль | Функция | Что шлёт в контракт |
|---|---|---|
| **Conductor** | Ведёт очередь, декомпозирует сцены, держит сроки | report (стадии), будущий дайджест-consumer (roadmap #1) |
| **Director** | Трактовка сцены (задача/сверхзадача/предлагаемые обстоятельства) | report перед генерацией |
| **Camera** | Варианты покрытия + рекомендация | decision_request (подтверждение продюсера) |
| **Actor/Disciple** | Генерация | report (взял в работу → ETA → готово: версия/сид/модель/стоимость/ссылка) |
| **Editor** | Сборка и ритм | report (версия сборки, замечания по стыкам) |
| **Continuity** | Консистентность между шотами | flag (расхождение, ссылка на конфликтующий шот) — **до приёмки, не после** |
| **Cost** | Смета и пороги | decision_request (approve, если оценка выше порога) |

**Нюанс:** прототип не обязан реализовывать всех семерых — `agents/` в структуре репозитория содержит `mock_camera.py, mock_actor.py, mock_continuity.py` (3 мока), этого достаточно, чтобы прогнать все 7 сценариев валидации. Остальные роли (Director, Editor, Cost, Conductor) — либо симулируются тем же mock-механизмом при необходимости для сценария 06 (Cost → payment-workflow), либо не нужны для MVP демо. **Решение:** добавить `mock_cost.py` как 4-й мок — без него сценарий 06 (превышение порога стоимости) нечем сгенерировать.

**Ключевое свойство присутствия агента (деки, стр. 6):** агент — не сервисный аккаунт с общим токеном, а **полноценный пользователь ClickUp** на отдельном домене (`camera.ivanov@agents.stanislavsky.ai`), с собственным аватаром, участием в Workload, историей действий. Это не косметика — это меняет архитектуру фильтра по автору (см. §5.1) и экономику (агенты — не платные места при отдельном домене/гостевой квоте).

**⚠ Риск, найденный ресёрчем API (не был виден из ТЗ/деки/архитектуры):** гостевые (Guest) аккаунты ClickUp, возможно, не могут выпустить себе Personal API Token (раздел Settings → Apps может быть недоступен роли Guest) — а без токена агент не может писать в ClickUp от своего имени через REST API, что деке и нужно ("агент неотличим от коллеги"). Если это подтвердится, "агенты = бесплатные Guest-места" из экономики деки не работает как есть. Подробный разбор и 3 варианта выхода — `03_clickup_requirements.md` §9. Это самый весомый найденный риск во всём документе — стоит проверить 30-минутным экспериментом до того, как экономика проекта закладывается в презентацию.

## 3. Разделение истины — где проходит граница на практике

Таблица "источник истины" из архитектуры звучит чисто, но на практике есть пограничные сущности, которые выглядят так, будто могут принадлежать обеим сторонам. Разберём их явно:

| Сущность | Кому принадлежит | Почему не очевидно |
|---|---|---|
| Статус задачи на доске (Backlog/…/Done) | **ClickUp** (визуально), но **производится** из stage в Stanislavsky | Stage — источник истины, статус ClickUp — его проекция. Человек может дёрнуть статус руками (Approved/Regenerate) — это **команда**, а не факт; она идёт через inbound-роутер, а не напрямую переписывает stage |
| Версия артефакта | **Stanislavsky** | ClickUp хранит только ссылку/номер версии как поле — если поле разошлось с реальной версией (сбой доставки), реконсиляция (roadmap #4) чинит это, не человек |
| Бриф (промпт/референс/нормирование) | **Человек через ClickUp** (поле задачи) | Но *исполнение* брифа и *когда именно* он применится ("обновляются до следующего запуска" — architecture §5) — решение Stanislavsky. Правка брифа не блокирует уже идущую генерацию текущей версии |
| Approve по стоимости | **Человек через ClickUp** (статус payment-workflow) | Но порог, оценка стоимости и что считать "оценка/факт" — расчёт Stanislavsky (Cost-агент) |
| correlation_id / идемпотентность | **Stanislavsky** (техническая деталь) | Не видна человеку в ClickUp вообще — не путать с task_id ClickUp |

**Вывод-нюанс:** "множества не пересекаются" верно для *данных*, но не для *эффектов* — правка брифа/approve/regenerate меняют то, что делает Stanislavsky. Граница проходит не по "кто может это изменить", а по **"что является источником правды, когда две системы расходятся во мнениях"**. Реконсиляция (roadmap #4) — это функция именно для этого случая, и её отсутствие в MVP означает: до её появления рассинхрон **не автоматически лечится**, только предотвращается конструкцией (идемпотентность + очередь с подтверждением). Это нормально для прототипа, но стоит явно писать в демо/защите: "самолечения пока нет, только защита от расхождения".

## 4. Три контракта — с уточнением того, что не сказано явно

### 4.1 AgentEvent (outbound) — расширение полей

Схема из `02_architecture.md` §2 — минимальная. При реализации не хватает полей, которые упоминаются текстом, но не в модели:

```python
class AgentEvent(BaseModel):
    kind: Literal["report", "decision_request", "flag"]
    agent_id: str                    # "camera.ivanov" — стабильный id, не email
    task_id: str                     # "SC-042/SHOT-07" — сквозной id шота
    stage: Stage
    correlation_id: str              # см. §5.2 — только outbound-идемпотентность
    payload: dict
    cost_usd: float | None
    requires_human: bool
    deadline: datetime | None

    # --- поля, подразумеваемые ТЗ/архитектурой, но отсутствующие в схеме §2 ---
    event_seq: int                   # монотонный номер события по task_id — упорядочивание/детект пропусков (см. §5.4)
    prev_agent_id: str | None        # кто вёл задачу до текущего (нужно роутеру для P3/R3, см. §4.3)
    thread_ref: str | None           # id родительского ClickUp-комментария, если событие — ответ в существующем треде
    version: str | None              # версия артефакта — вынесена из payload в поле верхнего уровня, т.к. используется фильтром/реконсиляцией напрямую, а не только для отображения
```

`payload: dict` осознанно остаётся свободным (не типизированным per-agent) — это прямой ответ на P2 ("все агенты имеют разный аутпут"): контракт стандартизирует **конверт**, а не содержимое. Внутри payload agent-специфичные поля (сид, модель, ETA, параметры) не валидируются ядром — это ответственность конкретного `agents/*` адаптера, который приводит сырой вывод агента к envelope. **Именно сюда лягут будущие примеры инпута агентов** — см. `06_open_questions.md`.

### 4.2 Фильтр — не бинарный, а с приоритетом по потолку частоты

Roadmap #3 ("потолок частоты — сообщения агента схлопываются в сводку") — это уже часть контракта фильтра, не отдельная фича вне ядра, если фильтр проектировать правильно с первого дня. **Решение для прототипа:** фильтр — не `bool`, а функция `AgentEvent -> FilterDecision`, где `FilterDecision ∈ {publish, publish_digest_only, drop}`. В MVP используется только `publish`/`drop` (roadmap #2/#3 добавляют третье значение через тот же интерфейс, без изменения ядра — именно это и обещано в §7 ТЗ "новый агент/трекер — без изменения ядра", распространяем принцип и на фильтр).

### 4.3 Router — конкретное правило вместо "разбор контекста реплики"

R3 говорит "разбор контекста реплики → доставка текущему агенту / новый тикет для агента прошлой итерации / эскалация" — это описание *результата*, не правило. Roadmap #7 прямо говорит, что сейчас роутинг **на правилах**, LLM — следующий шаг. Значит для прототипа нужно конкретное **детерминированное** правило. Предлагаемое (без NLP):

```
1. Входящий комментарий/событие привязан к ClickUp task_id (по определению — комментарий живёт в задаче).
2. Если task_id.stage ∈ {In Progress, Ready for Verification, Verification, Deferred}  → активная задача:
     - если есть @-упоминание конкретного agent_id → адресовано ему
     - иначе → адресовано текущему ведущему агенту задачи (agent_id последнего AgentEvent по этому task_id)
   Действие: доставить в контекст, агент отвечает в том же треде (R3, ветка 1)
3. Если task_id.stage == Done (задача закрыта и принята)  → комментарий пришёл "постфактум":
   Действие: создать НОВЫЙ тикет, приоритет = f(как давно закрыта, тон реплики — эвристика?), 
             ссылка на исходный task_id, prev_agent_id = agent_id последнего события исходной задачи (R3, ветка 2)
4. Если комментарий не резолвится ни в 2, ни в 3 (например: общий канал, не привязан к task_id, 
   или @-упоминание несуществующего agent_id) → эскалация человеку, производство не трогается (R3, ветка 3)
```

**Исправлено грилл-ревью (`07_grilled.md`, находка №2):** первая версия клала `Deferred` в ту же корзину, что и `Done` ("закрыта → новый тикет"). Это неверно по смыслу: `Deferred` — это "поставили на паузу", не "приняли и закрыли" — задача та же самая, просто ждёт своей очереди, и комментарий к ней («это всё ещё актуально?», «повысьте приоритет») почти всегда адресован **этой же** задаче, а не должен плодить новый тикет. Только `Done` (полностью принято, `Regenerate` для него больше не действие пайплайна) — настоящая "прошлая итерация" в смысле P3.

**Нюанс, которого нет в исходниках вообще:** правило в шаге 2 неявно предполагает, что "задача прошлой итерации" (P3) физически == "тот же ClickUp task_id, но уже закрытый", а не другой task_id. Это стыкуется с демо-трейсом деки (SC-042/SHOT-07 проходит Director→Camera→Actor→Continuity **в одной задаче**, через `Regenerate`), но стоит зафиксировать явно, потому что альтернативная модель (каждая regenerate-итерация = новый task_id) тоже правдоподобна и **ведёт к другой реализации роутера**. Мы фиксируем: **одна задача ClickUp = один шот, итерации = внутристадийные переходы (`Regenerate` возвращает в `In Progress`, не создаёт новый task_id)**. Новый task_id создаётся только роутером (ветка 3 выше), когда исходная задача уже закрыта.

### 4.4 Батчинг — sliding window с потолком (нюанс, отсутствующий в ТЗ)

Дословно: "комментарии в пределах временного окна разбираются как одно согласованное действие; комментарий после паузы открывает новое окно". Это **скользящее** окно (окно продлевается каждым новым комментарием), а не фиксированное окно от первого сообщения — иначе "пауза открывает новое окно" не имело бы смысла (при фиксированном окне пауза ничего не открывает, окно просто истекает).

**Проблема, которую ТЗ не рассматривает:** при чисто скользящем окне без потолка, человек, комментирующий раз в 55 секунд бесконечно, никогда не получит ответа агента — окно не закроется никогда. **Решение для прототипа:** добавить `max_batch_wait` (по умолчанию предлагаю 5 × window = 300 сек) — жёсткий потолок, после которого батч обрабатывается независимо от продолжающейся активности. Это не в исходном ТЗ — явное дополнение, см. `06_open_questions.md` для пометки "решение принято по умолчанию, не подтверждено пользователем".

## 5. Слой надёжности — операционализация

### 5.1 Защита от эха — конкретный механизм

**Обновлено по факту ресёрча ClickUp API** (см. `03_clickup_requirements.md` §7) — механизм ниже заменяет более раннее предположение "фильтр по email-домену как основной способ": домен в webhook payload попросту недоступен без дополнительного запроса, поэтому основной путь — allowlist по `user_id`, домен — вторичная проверка.

```
1. (основной) webhook.history_items[].user.id ∈ ALLOWLIST_AGENT_USER_IDS → эхо, не роутить как человеческую реплику
2. (fallback, требует доп. GET-запроса) email.domain == "agents.stanislavsky.ai" → используется только для неоднозначных случаев
```

ClickUp **не имеет** нативного поля "это бот/интеграция" (подтверждено — открытый нереализованный feature request в их публичном трекере). Это значит: agent_id↔clickup_user_id — обязательная таблица провижининга, заполняется вручную при создании агентских аккаунтов, и именно она (а не домен) — источник истины для anti-echo.

### 5.2 Идемпотентность — два разных id, а не один (нюанс/исправление терминологии)

ТЗ использует `correlation_id` для двух разных вещей:
- в AgentEvent (архитектура §2) — "идемпотентность, защита от дублей" **outbound**-стороны (повторная доставка того же события не публикует дубль в ClickUp);
- в R4/§5 архитектуры — "комментарии... собираются под одним correlation_id" — это **inbound**-группировка (батчинг).

Это два независимых пространства идентификаторов с разным временем жизни и разной семантикой (dedup vs grouping). **Решение:** развести в модели:
- `AgentEvent.correlation_id` — как в §2, генерируется агентом/адаптером, живёт вечно, используется TrackerAdapter для dedup при retry.
- `InboundBatch.batch_id` — генерируется Batcher'ом при открытии окна, живёт время окна + обработку, используется Router'ом как единица работы ("одна согласованная реакция").

### 5.3 Очередь с подтверждением — порядок и его пределы

"Досылается в исходном порядке" — фиксируем как **глобальный FIFO**, не per-task partitioning: см. `01_architecture_plan.md` §3 для обоснования и явного предела масштабирования (это узкое место при добавлении второго TrackerAdapter параллельно, но для прототипа с одним ClickUp-адаптером это самое простое корректное решение).

### 5.4 Дедлайн и молчание — оценка независима от доставки

Нюанс, которого нет в ТЗ: если ClickUp недоступен несколько часов (сценарий 07), а у decision_request был дедлайн внутри этого окна — дедлайн **не должен ждать восстановления связи**, чтобы сработать. Политика молчания — это внутренний scheduled-job Stanislavsky (проверка "есть ли ответ человека к дедлайну" по внутреннему состоянию), полностью независимый от здоровья исходящей очереди в ClickUp. Публикация *результата* применения политики молчания (например, "задача вернулась в Backlog") — уже идёт через обычную outbound-очередь и может встать в хвост при недоступности ClickUp, но само решение принимается вовремя.

**Найдено при грилл-ревью (`07_grilled.md`, находка №3) — гонка дедлайна с окном батчинга:** батчинг (§4.4) может держать реплику человека в открытом окне до 60с (потолок — до 300с), пока копит "согласованное действие". Если у decision_request короткий дедлайн (например, 2 минуты) и человек успел ответить, но его комментарий ещё сидит в открытом окне батчера — дедлайн-чекер, не зная об этом, может посчитать "человек не ответил" и применить политику молчания **поверх уже пришедшего, но не долетевшего до Router ответа**. **Правило (фикс):** дедлайн-чекер для конкретного `task_id` обязан сначала проверить, нет ли **открытого или необработанного** `InboundBatch`/`InboundEvent` по этому `task_id` — если есть, дедлайн считается формально не наступившим (событие "успело", даже если ещё не обработано), политика молчания не применяется, обработка идёт по обычному пути батчера. Это не требует менять контракты — только порядок проверки в scheduled-job.

**Дефолтный дедлайн, если агент его не указал:** `AgentEvent.deadline` — `Optional`; ТЗ не говорит, что происходит, если поле пустое, а `kind == "decision_request"`. Прототип использует дефолт `DEFAULT_DECISION_DEADLINE_MINUTES = 30` (значение — предположение, не подтверждено, см. `06_open_questions.md`), применяемый на границе (Filter/Router), если агент не проставил `deadline` явно.

## 6. Явные допущения этого документа

1. Один ClickUp task_id = один шот; итерации = переходы `Regenerate` внутри задачи (§4.3).
2. Комментарий на закрытой задаче → всегда новый тикет (никогда не переоткрывает исходную) (§4.3, ветка 3).
3. Батчинг — sliding window 60 сек + потолок 300 сек (§4.4) — потолок не из ТЗ, добавлен по умолчанию.
4. Агентские аккаунты идентифицируются по allowlist `clickup_user_id`, домен — вторичная проверка (§5.1, обновлено ресёрчем API).
5. correlation_id (outbound) и batch_id (inbound) — разные пространства id (§5.2).
6. Очередь — глобальный FIFO, без per-task партиционирования (§5.3).
7. Для сценария 06 (порог стоимости) в `agents/` нужен `mock_cost.py`, не упомянутый явно в структуре репозитория (§2).
8. Лицензирование агентских аккаунтов как бесплатных Guest — **не подтверждено**, требует эксперимента (§2, риск); есть 3 fallback-варианта, ни один не меняет ядро.
