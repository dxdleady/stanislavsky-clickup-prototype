# План прототипа: порядок сборки

> Как собрать `prototype/` так, чтобы на каждом шаге было что показать и что assert'ить. Единица планирования — не "неделя", а **сценарий валидации** (ТЗ §4): пока сценарий не зелёный, следующий не начинается, потому что каждый следующий сценарий опирается на инфраструктуру предыдущего.

**Статус (2026-08-13): фазы 0-5 и 7 реализованы, все 7 сценариев ТЗ зелёные на `memory.py`.** `make demo` (`python -m sim.runner`) и `pytest prototype/` — оба зелёные. Живой демо-слой (см. ниже) слит с основной последовательностью фаз, а не остаётся отдельным срезом: `inbound/router.py` теперь настоящий `RuleBasedRouter` (Фаза 2), `inbound/batcher.py` — настоящее скользящее окно (Фаза 3), `core/filter.py`/`core/outbound_queue.py` реализованы (Фазы 1/5). Один сознательный технический сдвиг относительно этого документа: LLM-провайдер для живого демо-среза — **Qwen** (Alibaba, OpenAI-совместимый эндпоинт), не Claude — у пользователя нет отдельного Anthropic-ключа для рантайма (Claude Code — это доступ к самому Claude, не то же самое, что ключ для `ANTHROPIC_API_KEY` в приложении). Подробности — `11_live_demo_architecture.md`. Файлы сценариев называются `sim/scenarios/s01_*.py` … `s07_*.py` (префикс `s`, не голая цифра — `01_x.py` не импортируется в Python, это опечатка в документах ниже, не в коде). Фаза 6 (реальный ClickUp-адаптер) частично пройдена — `adapters/clickup.py`/`inbound/webhook.py` реально работают против настоящей доски (см. `11_live_demo_architecture.md`), но не прогнаны там все 7 сценариев ТЗ — сделано под демо-звонок, не под формальную приёмку.

## Принцип: sim/scenarios как driver разработки

`sim/scenarios/0N_*.py` пишутся **до** реализации фичи, красные — заглушки реализуются, пока не позеленеют (TDD на уровне сценариев, не только юнитов). `make demo` в конце — это просто последовательный прогон всех `sim/scenarios/*` с человекочитаемым выводом; отдельного "демо-режима" в коде быть не должно — демо и тесты буквально одна кодовая база (ТЗ §5, последняя строка — это не пожелание, а архитектурное требование к `sim/runner.py`).

## Фаза -1 — спайк по лицензированию агентов (30 минут, можно параллельно с чем угодно)

Не блокирует разработку на `memory.py` (фазы 0-5), но блокирует **экономику**, которую дека закладывает в презентацию. Ресёрч ClickUp API (`03_clickup_requirements.md` §9) нашёл риск: Guest-аккаунт, возможно, не может сгенерировать Personal API Token, а без него агент не может писать в ClickUp от своего имени. Спайк: завести один тестовый Guest-аккаунт на отдельном домене, попробовать Settings → Apps → Generate Token. Результат определяет, остаётся ли в силе план "7 бесплатных агентских мест" или нужен fallback (платные Member-места / общий интеграционный аккаунт — оба варианта не требуют изменений в `core/`). Сделать **до** фиксации бюджета проекта в любых внешних материалах.

## Фаза 0 — скелет без I/O (0.5–1 день)

Цель: `core/` компилируется и покрыт юнит-тестами, ничего не зависит от сети/ClickUp.

- `core/events.py` — `AgentEvent`, `InboundEvent`, `InboundBatch`, `FilterDecision` (см. `01_architecture_plan.md` §2)
- `core/state_machine.py` — `Stage`, переходы, `REWORK_COST_MULTIPLIER`
- `core/clock.py` — `Clock`, `RealClock`, `FakeClock`
- `core/ids.py` — генерация `correlation_id` (uuid4), `batch_id`, монотонный `event_seq` per task_id
- Юнит-тесты: валидация модели, переходы состояний (недопустимые переходы кидают ошибку), `FakeClock.advance()`

**Критерий готовности:** `pytest prototype/core/` зелёный, нет ни одного импорта из `adapters/`/`inbound/`.

## Фаза 1 — outbound happy path → сценарий 01 (1 день)

Цель: `sim/scenarios/01_happy_path.py` зелёный на `memory.py`.

- `adapters/base.py` (протокол) + `adapters/memory.py` (in-memory реализация)
- `core/filter.py` — `publish`/`drop` по правилам из YAML (без digest пока)
- Очередь: простой `asyncio.Queue` (или список + индекс) с подтверждением — глобальный FIFO
- `agents/mock_actor.py` — единственный мок, достаточный для happy path (взял в работу → готово)
- `sim/scenarios/01_happy_path.py`: наполнить бэклог → провести через все стадии без вмешательств → assert: все переходы стадий видны в ленте memory-адаптера в правильном порядке

**Критерий готовности:** `make demo -- --scenario 01` печатает трейс, похожий на демо-ленту из деки (§4.5 в `01_architecture_plan.md`).

## Фаза 2 — inbound skeleton + роутинг → сценарии 02, 03, 05 (1.5–2 дня)

Цель: входящие события (пока — синтетические `InboundEvent`, не настоящий webhook) доходят до `Router` и правильно классифицируются.

- `inbound/router.py` — `RuleBasedRouter` по правилу из `00_overview.md` §4.3
- `inbound/batcher.py` — пока без реального таймера (используем `FakeClock`)
- `agents/mock_camera.py`, `agents/mock_continuity.py` — нужны для реалистичной цепочки (Camera рекомендует → Continuity флагает)
- Три сценария параллельно, т.к. используют общую инфраструктуру Router:
  - `02_reply_to_current_agent.py` — реплика доставлена в контекст, агент отвечает в треде
  - `03_reply_to_previous_iteration.py` — новый тикет, приоритет, ссылка на исходный
  - `05_out_of_context_noise.py` — эскалация, производство не тронуто

**Критерий готовности:** все три сценария зелёные на `memory.py`; `Router` не знает о ClickUp вообще (принимает/возвращает только `core`-модели).

## Фаза 3 — батчинг → сценарий 04 (0.5–1 день)

Цель: `inbound/batcher.py` с реальной sliding-window логикой на `FakeClock`.

- Sliding window 60с + потолок 300с (см. `00_overview.md` §4.4 — потолок это допущение прототипа, пометить в коде комментарием со ссылкой на `06_open_questions.md`)
- `04_batched_comments.py`: подряд идущие реплики → один `InboundBatch`/одна реакция; реплика после паузы → новый `batch_id`

**Критерий готовности:** тест двигает `FakeClock` вручную (без реального `sleep`), проверяет и sliding-часть, и потолок.

## Фаза 4 — стоимость и переделка → сценарий 06 (1 день)

Цель: `agents/mock_cost.py` + логика эскалации approve из `01_architecture_plan.md` §3.

- Реализовать формулу `estimated_rework_cost` и три ветки (доработка / новая итерация / эскалация)
- Payment-workflow как отдельная сущность в `TrackerAdapter` (в `memory.py` — просто отдельный тип задачи с полем `blocks_task_id`)
- Идемпотентность approve (§4.5 sequence) — обязательно тестировать двойной approve в этом же сценарии, не откладывать на фазу 5
- `06_cost_threshold.py`: генерация блокируется → payment-workflow создан → approve → генерация продолжается → повторный approve не дублирует

**Критерий готовности:** явный assert на "количество вызовов генерации == 1" после двойного approve.

## Фаза 5 — надёжность очереди → сценарий 07 (0.5–1 день)

Цель: `memory.py` умеет симулировать недоступность ("ClickUp упал"), очередь копится и досылается по порядку.

- Добавить в `TrackerAdapter`-протокол возможность инжектить сбой (для `memory.py` — флаг `simulate_outage`)
- Backoff + ретрай в очереди (для памяти — просто счётчик попыток, без реальных задержек благодаря `Clock`)
- `07_clickup_down.py`: события копятся во время "недоступности", восстановление → порядок доставки == порядку постановки

**Критерий готовности:** все 7 сценариев `make demo` зелёные на `memory.py` — это и есть "критерий сдачи" из ТЗ §4.

## Фаза 6 — реальный ClickUp adapter + webhook (2–3 дня, зависит от ресёрча API)

Цель: то же поведение, что в фазах 1–5, но говорит с настоящим ClickUp.

**Перед стартом фазы — обязательный ручной чек-лист** (не код, но в критическом пути; полный список — `03_clickup_requirements.md` §10): статусы и custom fields в ClickUp API не создаются программно, только руками в UI — создать их, завести агентские аккаунты и Personal API Token'ы, зарегистрировать webhook, заполнить таблицу `agent_id ↔ clickup_user_id`.

- `adapters/clickup.py` реализует тот же `TrackerAdapter`-протокол — если фазы 0–5 сделаны честно (Router/Filter/core не знают про ClickUp), этот шаг **не должен трогать ничего вне `adapters/clickup.py` и `inbound/webhook.py`**. Если приходится лезть в `core/` — сигнал, что контракт спроектирован неправильно раньше.
- `inbound/webhook.py` — FastAPI-эндпоинт, регистрация webhook в ClickUp, верификация подписи (см. `03_clickup_requirements.md`)
- Прогнать те же 7 сценариев `sim/` на реальном ClickUp-тестовом Space вручную (не в CI — нужен токен) — сверить, что лента в ClickUp выглядит как демо-трейс из деки

**Критерий готовности:** ТЗ §4, последняя строка — "ClickUp-адаптер подключается реальным токеном без изменений ядра". Это буквально критерий приёмки, не метафора — проверяется diff'ом (изменения вне `adapters/clickup.py` и `inbound/webhook.py` при подключении адаптера означают провал этого критерия).

## Живой демо-слой (для конкретного звонка) — теперь слит с основной последовательностью фаз

**Обновление (2026-08-13): слияние произошло.** То, что ниже описывалось как "параллельный, упрощённый срез", теперь использует ту же инфраструктуру, что и остальные фазы — не два несвязанных набора кода:

- `inbound/router.py` — настоящий `RuleBasedRouter` (Фаза 2), общий для `sim/` и для потенциального прямого inbound-пути; LLM-классификация под конкретно живой ClickUp-демо переехала в отдельный файл `inbound/comment_router.py::CommentRouter` (был техдолг — этот класс раньше назывался `RuleBasedRouter`, хотя был LLM-путём, см. `11_live_demo_architecture.md` §6, закрыт этим переименованием).
- `inbound/batcher.py` — настоящее скользящее окно 60с + потолок 300с (Фаза 3), не pass-through-заглушка. Меняет UX живого демо: ответ агента больше не мгновенный, у него теперь то же окно, что и в сценарии 04.
- `core/filter.py`, `core/outbound_queue.py` — реализованы (Фазы 1/5), используются и `sim/system.py`, и (частично, где применимо) живым путём.
- LLM-провайдер живого демо-среза (`inbound/comment_router.py::classify_comment`, `agents/live_demo_agent.py::generate_reply`) — **Qwen** (`core/llm.py`), не Claude Haiku 4.5, как было написано здесь изначально. Причина смены — не техническая, а по доступу: у пользователя нет отдельного `ANTHROPIC_API_KEY`.

Что по-прежнему упрощено ради демо-звонка (явно, не молчаливым сокращением):
- Проверка HMAC-подписи (§2.4 `03_clickup_requirements.md`) реализована, но выключена по умолчанию (`REQUIRE_WEBHOOK_SIGNATURE=false`).
- Все 7 сценариев ТЗ не прогонялись на реальном ClickUp (только на `memory.py` через `sim/`) — Фаза 6 в полном объёме (custom fields, 7 агентских аккаунтов) не пройдена, только узкий срез под 1 бот-аккаунт и 4 демо-задачи, см. `11_live_demo_architecture.md` §3.

Ручной чек-лист настройки ClickUp под этот срез — `11_live_demo_architecture.md` §3.
