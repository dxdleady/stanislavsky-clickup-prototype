# Архитектура: Workflow Control Layer

## 1. Принцип: проектируем от контрактов, а не от процесса

Скрам-доска со столбцами — представление. Основа системы — три контракта:

1. **Что агент обязан сообщить** — единый формат событий.
2. **Что из этого попадает человеку** — конфигурируемый фильтр.
3. **Как реплика человека возвращается в систему** — роутер обратного канала.

Любой агент, отдающий событие по контракту, подключается без доработок ядра. Любой трекер с написанным адаптером заменяет ClickUp.

### Разделение ответственности

| | Stanislavsky (дом) | ClickUp (представительство) |
|---|---|---|
| Источник истины | Производство: версия, стадия, артефакт, стоимость | Решения человека: approve, приёмка, бриф, назначение |
| Что живёт | Внутренний обмен агентов, ретраи, черновые проходы | Лента задачи, дайджесты, эскалации, статусы |

Множества не пересекаются — рассинхрон невозможен по построению.

### Общая схема

```
           OUTBOUND                                INBOUND
┌──────────────┐   AgentEvent   ┌─────────┐   ┌──────────────┐
│    Агенты    │ ─────────────▶ │ Очередь │   │   Webhook    │ ◀── ClickUp
│ (Stanislav.) │                │ + подтв.│   │   (FastAPI)  │     (комментарий,
└──────────────┘                └────┬────┘   └──────┬───────┘      статус, бриф)
                                     ▼               ▼
                               ┌──────────┐    ┌──────────┐
                               │  Фильтр  │    │  Batcher │ (окно 60с)
                               └────┬─────┘    └────┬─────┘
                                    ▼               ▼
                            ┌──────────────┐  ┌──────────┐
                            │TrackerAdapter│  │  Router  │──▶ контекст агента /
                            │clickup|memory│  └──────────┘    новый тикет /
                            └──────┬───────┘                  команда пайплайну /
                                   ▼                          эскалация
                                ClickUp
```

## 2. Единый контракт событий (AgentEvent)

Сводит разнородный аутпут агентов к одному стандарту и реализует три формата ленты (Отчёт / Запрос решения / Флаг):

```python
class AgentEvent(BaseModel):
    kind: Literal["report", "decision_request", "flag"]
    agent_id: str            # camera.ivanov
    task_id: str             # SC-042/SHOT-07
    stage: Stage             # см. машину состояний
    correlation_id: str      # идемпотентность, защита от дублей
    payload: dict            # версия, сид, модель, ссылка, ETA, параметры
    cost_usd: float | None   # оценка/факт стоимости
    requires_human: bool     # требует ли реакции человека
    deadline: datetime | None  # дедлайн ответа для decision_request
```

Агент шлёт событие на каждой смене стадии — по ленте видно движение задачи.

## 3. Машина состояний со стоимостью переделки

```
Backlog → Planned → In Progress → Verification → Done
                         ↑              |
                         └── Regenerate ┘
                    (+ Deferred из любой стадии)
```

Каждая стадия несёт `rework_cost_multiplier`. Роутер использует его при выборе действия на реплику человека: вернуть на доработку, создать новый тикет или эскалировать на approve (если переделка дороже порога). Длина спринта и набор стадий — конфигурация.

## 4. Outbound-пайплайн: агент → человек

```
AgentEvent → очередь с подтверждением → Фильтр → TrackerAdapter → ClickUp
```

- **Фильтр** — конфиг с правилами, не хардкод. Дублируется в ClickUp: решения с обоснованием, готовые результаты, запросы к человеку, проблемы, смены стадий, превышения бюджета. Остаётся дома: внутренний обмен агент↔агент, промежуточные проходы, авто-восстановленные сбои, микросостояния.
- **TrackerAdapter** — интерфейс с двумя реализациями: `clickup.py` (реальный API) и `memory.py` (in-memory для тестов и демо без токена). Замена ClickUp на Linear/Jira = один новый адаптер.

## 5. Inbound-роутер: человек → агент

Вебхук ClickUp принимает событие (комментарий, смена статуса, правка поля брифа, @-упоминание) и классифицирует:

| Реплика | Действие |
|---|---|
| Адресована текущему агенту задачи | В его рабочий контекст; агент отвечает в том же треде |
| Относится к агенту предыдущей итерации | Новый тикет с приоритетом и ссылкой на исходный |
| Смена статуса (Approved / Regenerate) | Команда пайплайну: пропустить дальше / новая итерация с референсом |
| Правка поля брифа | Промпт/референс/нормирование обновляются до следующего запуска |
| Вне контекста | Лог + эскалация человеку; производство не трогается |

**Батчинг.** Комментарии в пределах окна (60 сек) собираются под одним `correlation_id` и разбираются пачкой — одна согласованная реакция вместо каскада итераций. Пауза открывает новое окно.

## 6. Слой надёжности

- **Фильтр по автору** — событие от агентной учётки не возвращается агенту как человеческая реплика (защита от эха).
- **Идемпотентность по `correlation_id`** — повторный approve не запускает вторую генерацию; ретрай доставки не публикует дубль.
- **Очередь с подтверждением** — ClickUp недоступен → производство идёт, события копятся и досылаются в исходном порядке.
- **Политика молчания** — нет ответа до дедлайна → стадия действует по политике: рекомендация агента либо пауза.

## 7. Представление для человека

### Доска (Board view, столбцы = стадии)

```
Бэклог │ Спринт │ В прогрессе │ Готово к верификации │ Верификация │ Выполнено │ Отложено
```

Карточка: ведущий агент, стадия, стоимость (оценка/факт), ETA, версия последнего артефакта. Новый столбец = новая стадия в конфиге.

### Лента задачи (Activity view)

Хронология в человекочитаемом виде: кто взял, что решил, что готово, где ждут человека. Три формата событий визуально различимы.

### Дешборды

- **Спринт:** burndown, что горит, где дольше всего ждут решения человека.
- **Стоимость:** расход $ и GPU-минут по сценам/агентам, задачи выше порога.
- **Вмешательства:** сколько правок на какой стадии — данные для ретроспективы.

Всё собирается штатными средствами ClickUp (Board, Dashboards, custom fields) — заполняются из полей AgentEvent, разработка UI не нужна.
