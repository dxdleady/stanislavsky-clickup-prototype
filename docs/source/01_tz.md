# ТЗ: Workflow Control Layer для мультиагентного производства

Прототип интеграции агентной системы (Stanislavsky) с ClickUp: человек видит работу агентов и может вмешаться на любом этапе — система корректно это отрабатывает.

---

## 1. Дано

Агенты работают независимо и выполняют поставленные задачи. Мультиагентная система живёт в Stanislavsky; ClickUp — представительство, где работа видна и где в неё вмешивается человек.

## 2. Проблемы

| # | Проблема |
|---|---|
| P1 | Законченные задачи не логируются в управляемый контур. Нет инструмента явного контроля результата, нельзя вмешаться сходу и скорректировать процесс |
| P2 | Все агенты имеют разный аутпут. Нужен единый стандарт, который легко читать и интерпретировать — человеку и машине |
| P3 | Комментарии под задачей не всегда явно относятся к агенту, который её выполнял, — могут неявно относиться к другому (например, к предыдущей итерации) |
| P4 | Под одной задачей может быть несколько комментариев — подряд и с паузой. Каждый нужно разобрать, но реагировать по одному — плодить лишние итерации |
| P5 | Задача может быть на разном этапе — и стоимость переделки на каждом этапе разная. Система должна это учитывать |
| P6 | Реплика человека может не успеть разобраться до заданного срока — нужно определённое поведение по дедлайну |

## 3. Требования к решению

### Функциональные

| Треб. | Описание | Закрывает |
|---|---|---|
| R1 | Воркфлоу по типу скрама со стадиями: Бэклог → Спринт → В прогрессе → Готово к верификации → Верификация → Выполнено (+ Отложено). Флоу расширяется конфигурацией, а не переписыванием | P1 |
| R2 | Единый формат ответа агентов: агент шлёт стандартизированный статус на каждой стадии — видно, как задача движется | P2 |
| R3 | Роутер входящих комментариев по активным тикетам: разбор контекста реплики → доставка текущему агенту / новый тикет с приоритетом для агента прошлой итерации / эскалация, если вне контекста | P3 |
| R4 | Батчинг реплик: несколько комментариев в пределах временного окна разбираются как одно согласованное действие; комментарий после паузы открывает новое окно | P4 |
| R5 | Учёт стоимости переделки по стадиям: реакция на правку зависит от этапа — доработка, новый тикет или эскалация на approve, если переделка дороже порога | P5 |
| R6 | Дедлайн у запросов решения + политика молчания: не ответили в срок → рекомендация агента либо пауза, возврат задачи в бэклог/туду | P6 |
| R7 | Длина спринта — параметр конфигурации, задаётся по возможностям агентов | — |
| R8 | Управление человеком из ClickUp без выхода: комментарий, @-упоминание, смена статуса (Approved/Regenerate), правка брифа, approve стоимости | P1 |

### Нефункциональные

- **Расширяемость:** новый агент подключается реализацией контракта событий; новый трекер — реализацией адаптера. Ядро не меняется.
- **Надёжность:** защита от эха (фильтр по автору), идемпотентность (повторный approve не запускает вторую генерацию), очередь с досылкой при недоступности ClickUp.
- **Разделение истины:** производство (версия, стадия, артефакт, стоимость) принадлежит Stanislavsky; решения человека (approve, приёмка, бриф, назначение) — ClickUp. Множества не пересекаются.

## 4. Валидация

Симулятор создаёт полноценный бэклог на спринт, проводит агентов через все состояния и имитирует комментарии в разные моменты имплементации. Каждый сценарий — набор assert'ов.

| # | Сценарий | Что проверяем |
|---|---|---|
| 01 | Happy path | Бэклог → Done без вмешательств; все смены стадий видны в ленте |
| 02 | Правка текущему агенту | Реплика доставлена в контекст, агент ответил в треде, задача обновлена |
| 03 | Правка агенту прошлой итерации | Новый тикет создан, приоритет назначен, ссылка на исходный, старая задача закрыта/обновлена |
| 04 | Пачка комментариев (подряд и с паузой) | Подряд — объединены в одно действие; после паузы — новое окно |
| 05 | Рандомный коммент вне контекста | Производство не тронуто, реплика залогирована и эскалирована |
| 06 | Превышение порога стоимости | Генерация заблокирована, payment-workflow создан, повторный approve не запускает дубль |
| 07 | Недоступность ClickUp | Очередь копится, после восстановления досылается в исходном порядке |

**Критерий сдачи:** `make demo` запускает все сценарии на memory-адаптере с зелёным прогоном; ClickUp-адаптер подключается реальным токеном без изменений ядра.

## 5. Представление прототипа: сценарий демо (10 минут)

1. **Старт.** `make demo` — симулятор наполняет бэклог спринта, агенты разбирают задачи. На доске видно движение карточек по столбцам.
2. **Вмешательство №1.** Комментарий текущему агенту («убери контровой») — агент отвечает в треде, задача уходит на новую итерацию, стоимость пересчитана.
3. **Вмешательство №2.** Правка, относящаяся к агенту прошлой итерации — на доске новый тикет с приоритетом и ссылкой на исходный.
4. **Шум.** Рандомный коммент вне контекста — производство не дёргается, реплика в логе эскалаций.
5. **Деньги.** Задача превышает порог стоимости — генерация встала, в ленте payment-запрос; approve — поехала дальше.
6. **Финал.** Спринт-дешборд: что сделано, где вмешивался человек, сколько потрачено. Мостик к ретроспективе и roadmap.

Каждый шаг демо — один из сценариев валидации, показанный вживую. Демо и тесты — одна кодовая база.
