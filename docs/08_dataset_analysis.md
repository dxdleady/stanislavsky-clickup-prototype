# Разбор демо-датасета (костюмный цех) — что меняется в плане

> Источники: `docs/source/stanislavsky_costume_demo_dataset.json` (v1) и `_v2.json` (v2, `supersedes: "1.0"` — считаем v2 главным, v1 держим для сравнения). Это не абстрактный пример — это полноценный сценарий одного съёмочного дня (СД-04, проект «Тихий берег») с каталогом типов сообщений, escalation-политиками, правами агентов на поля и метриками. Фактически — то самое обещанное "примеры инпута агентов", только гораздо полнее.

**Важная оговорка от автора датасета (2026-08-12, в разговоре):** оба файла сгенерированы Клодом по концепции сервиса ("в том виде, в каком он должен быть"), просмотрены по диагонали, гарантий точности нет. Это меняет вес находок ниже: датасет — **второй авторский прогон той же концепции**, а не независимо собранные реальные данные. Там, где ниже написано "подтверждено" — читать как "второй непротиворечивый пример", не как независимое доказательство. Где написано "два независимых источника" (находка №3, В4 в `06_open_questions.md`) — это тоже "деки-трейс + Клод-сгенерированный датасет", в конечном счёте два прогона одной и той же модели по одному и тому же ТЗ, а не два разных наблюдения реальности.

## Как это устроено (коротко)

Датасет — не сырые логи реального агента, а **авторский демо-сценарий** для показа: `accounts` (агенты/люди/упомянутые-вне-демо), `workspace` (Space/List/Chat), `statuses`, `custom_fields`, `costume_plot` (предметная модель цеха), `tasks` (9 задач), `message_types` (v2 — каталог MT-01…MT-24, MT-90), `escalation_policies` (v2), `events` (хронология 60-68 событий), `demo_cases` (указатели на события по сценарию), `metrics`/`economics`, `visualization_hints`. Это одновременно (а) источник для `sim/scenarios/*` — почти готовый сценарий для симулятора, и (б) конкретизация контракта `AgentEvent` на новом домене (костюмы, не камера/генерация).

## Находка №1 (важная, требует правки кода) — стадии не единый enum, а per-домен конфигурация

`core/state_machine.py` (и `docs/01_architecture_plan.md` §3) были построены на 7 стадиях из `01_tz.md` §3 (Backlog/Planned/In Progress/Ready for Verification/Verification/Done/Deferred) как на **фиксированном** `Literal`-типе. Датасет костюмного цеха использует **другой** набор статусов ClickUp:

```
Backlog, Ready for Director, Wardrobe Check, Coverage Review,
Cost Approval, In Generation, QC, Regenerate, Accepted, Blocked
```

Это не опечатка и не отступление от ТЗ — это ожидаемое следствие R1 ("флоу расширяется конфигурацией, а не переписыванием"), которое я в первой версии кода не довёл до конца: захардкодил один `Stage = Literal[...]` вместо того, чтобы сделать набор стадий параметром конфигурации per-List/per-домен. Костюмный цех и камера/генерация — это, вероятно, **два разных workflow** (два List'а ClickUp с разными наборами статусов), не одна абстрактная 7-стадийная машина с ремаппингом.

**Исправлено в коде** (`prototype/core/state_machine.py`, `prototype/core/events.py`):
- `Stage` теперь `str`, не `Literal[...]` — конкретный набор значений задаётся `WorkflowConfig`, не типом.
- `WorkflowConfig` — pydantic-модель: `stages: dict[str, StageDefinition]`, `transitions`, `closed_stages`.
- `StageDefinition` несёт `waits_for_human`, `active_for_routing` (P3-правило, находка №2 грилла — Deferred/Blocked не значит "закрыто"), `rework_branch` (cheap_edit/needs_regeneration — находка №4 грилла), `escalation` (см. находку №2 ниже).
- Заведены **две** конкретные конфигурации: `CAMERA_PIPELINE` (из исходного ТЗ/архитектуры) и `COSTUME_PIPELINE` (из этого датасета, с реальными статусами/эскалациями). Наличие двух живых конфигураций — это не просто "теперь можно" в тексте документа, а рабочий тест на то, что архитектура действительно не завязана на один флоу.

## Находка №2 — политика молчания: были предположения, теперь есть настоящие числа

`00_overview.md` §5.4 и `06_open_questions.md` В5 предполагали, что политика молчания (P6/R6) конфигурируется per-decision-type, но конкретных чисел не было — "допущение, не подтверждено". Датасет даёт готовую таблицу `escalation_policies` (v2):

| Стадия | Таймаут | Действие | Кому эскалировать | Повтор |
|---|---|---|---|---|
| `cost_approval` | 30 мин | пауза (деньги без человека не тратятся) | Тимур | нет |
| `regenerate` | 20 мин | применить рекомендацию агента | Супервайзер | нет |
| `coverage_review` | 30 мин | применить рекомендацию агента | Супервайзер | нет |
| `blocked` | 240 мин (4ч) | **повторная эскалация** | Продюсер, Первый ассистент | **да** |

**Это закрывает В5 почти полностью** — не нужно гадать, "рекомендация или пауза": это конфигурация per-стадия, ровно как я предполагал в архитектуре, и вот конкретные дефолты для одного реального домена. **Новое, чего не было в моей модели:** `repeat: true` для `blocked` — не единоразовое действие по дедлайну, а периодическая нагрузочная эскалация, пока задача не разблокирована (пример в датасете: SC-041/02 висел в Blocked 32 часа, получил повторные эскалации). Это третий вид политики молчания, не предусмотренный в `01_architecture_plan.md` изначально (`on_timeout: auto_apply_recommendation | pause_and_requeue`) — добавлен `repeat_escalation`.

**Исправлено:** `EscalationPolicy` (см. находку №1) — `action: Literal["pause", "apply_agent_recommendation", "repeat_escalation"]`, `repeat: bool`. `06_open_questions.md` В5 сужен: общий механизм подтверждён, остаётся уточнить только дефолты для camera-домена (пока используются числа из демо-трейса деки, где они есть — approve по деньгам, остальное не описано).

## Находка №3 — В4 подтверждён датасетом, снимается с открытых вопросов

`06_open_questions.md` В4 ("один task_id = один шот, итерации — переходы внутри задачи, без нового task_id") был самым структурным допущением всего плана, выведенным из одного демо-трейса деки. Датасет даёт **второй независимый пример**, который ведёт себя точно так же: `SC-042/08` проходит `backlog → in_generation → qc → regenerate → qc → accepted` **в одной и той же задаче** (`state_history` в `tasks[]`, событие E040 меняет `wardrobe_ref` и статус на `regenerate` без создания нового task_id). Два независимых источника, согласных друг с другом — допущение повышается из "предположение" в "подтверждено демо-материалами", снимается с открытых вопросов.

## Находка №4 — новый архитектурный элемент: каталог `message_types` (MT-01…MT-24)

Ничего подобного не было в ТЗ/архитектуре явно, но это ценная идея, которую стоит перенять: датасет документирует **протокол** — не только формат конверта (`AgentEvent`), но и **каталог типов сообщений** между конкретными ролями, каждый с `from`/`to`/`trigger`/`payload`-полями/`expects` (следующее ожидаемое сообщение)/`sla`/`format`/иногда `rule` (например, MT-12: `"ответ строго бинарный, промежуточные формулировки невалидны"`).

**Почему это важно для P2 (единый формат) и открытого вопроса В2 (стиль комментариев):** каталог типов сообщений — это ровно то место, где фиксируется "стиль" — не как общее пожелание, а как конкретное структурное и тональное правило **на конкретный тип сообщения**. MT-12 — лучший пример: "Подтверждение готовности бинарно: готов / не готов + причина + срок. Формулировки вида «постараемся» невалидны" (это же в `process_invariants` верхнего уровня v2). Это первый настоящий, а не гипотетический ответ на В2 — пусть и для одного конкретного типа сообщения, не для всех.

**Рекомендация (не блокирует прототип, но стоит держать в голове для Фазы 2 роутинга):** `payload: dict` в `AgentEvent` остаётся неструктурированным на уровне контракта (P2 требует именно это), но каждый **конкретный** `(agent_id, kind)` может иметь задокументированный (не обязательно валидируемый кодом в MVP) `message_type` с ожидаемыми полями — как соглашение между агентом-автором и `Router`/`Filter`, а не как runtime-схема. Это не новое поле контракта, а слой документации/конфигурации поверх него — аналогично тому, как `filter_config.yaml` уже конфигурирует поведение без изменения `core/`.

## Находка №5 — dedup-окно ограничен по времени, не бесконечен

`03_clickup_requirements.md`/scaffold-код хранили `processed_correlation_ids` как растущее без ограничения множество ("подтверждено ли когда-либо"). Датасет прямо указывает `dedup_window_sec: 900` (15 минут) для идемпотентного approve (E029/E030 v2). Это практичное уточнение: для прототипа хранить всё бесконечно не вредно (объём мал), но для реального сервиса это сигнал, что idempotency-стор может быть TTL-кэшем (15 минут достаточно, чтобы покрыть ретраи ClickUp — вспомним из `03_clickup_requirements.md` §2.5: до 5 ретраев с таймаутом 7с каждый, то есть весь ретрай-цикл ClickUp укладывается в секунды-минуты, не часы). Не блокирующая правка, зафиксирована как уточнение к находке №6 грилла (`07_grilled.md`) — не меняет решение "БД не нужна", но даёт конкретный TTL на будущее.

## Находка №6 — outbound rate-ceiling (roadmap #3) — теперь с конкретным примером, и это НЕ то же самое, что inbound-батчинг (R4)

Событие E055 (v2): "Всплеск трансляции — 34 события за 3 мин... 12 отчётных сообщений схлопнуты в сводку", приоритет — decision_request/flag. Это ровно `rate_ceiling`/`publish_digest_only` из `01_architecture_plan.md` §8 (roadmap #3) — **исходящая** сторона (агенты → человек). Стоит явно развести с R4 (входящий батчинг человеческих комментариев, окно 60с) — **датасет не содержит ни одного примера R4-сценария** (несколько комментариев человека подряд/с паузой). Это не противоречие, а честный пробел источника: R4 всё ещё нужно тестировать синтетически (как уже сделано в `04_test_plan.md`, сценарий 04), датасет не даёт для него готового трейса.

## Находка №7 — права агента на поля/статусы (`clickup_permissions`) смыкаются с найденным в ресёрче ClickUp API

`accounts.agents[].clickup_permissions.{fields_write, statuses_write}` (v2) + `owns`/`cannot` — явные списки того, что каждый агент вправе писать. Это смыкается с находкой ресёрча в `03_clickup_requirements.md`: Business Plus даёt **Advanced Custom Field Manager** — возможность ограничивать право редактирования конкретных custom fields по ролям **средствами самого ClickUp**, не кодом нашего адаптера. Рекомендация: там, где можно — заводить это как разрешения ClickUp (декларативно, административно), а не как runtime-проверку в `clickup.py`; там, где ClickUp не даёт нужной гранулярности — фиксировать как документацию (`agents/<agent>/permissions.yaml`) и заводить юнит-тест "агент X не пытается писать в поле не из своего owns" на моках, не как security-контроль (агенты не злонамеренные, это самоконтроль корректности интеграции).

## Находка №8 — экономика деки подтверждена независимым источником

`economics` (v2): `paid_seats: 8, free_service_agents: 3, plan_target: "Business Plus"` — совпадает с Alliance Deck дословно ("8 платных мест... 3 служебных агента бесплатно"). Независимое подтверждение целевой модели, но **не** отменяет риск, найденный ресёрчем API (`03_clickup_requirements.md` §9: неясно, может ли Guest получить Personal API Token) — датасет описывает целевую *модель*, не подтверждает её техническую реализуемость. Три перечисленных в датасете агента (`producer`, `first_ad`, `costume`) все имеют `"seat": "free_guest"` — это именно те три аккаунта, для которых нужно провести 30-минутный спайк из `02_prototype_plan.md` Фазы -1, прежде чем полагаться на экономику.

## Находка №9 (не архитектурная, но полезная для теста/UI) — "продюсер переопределил рекомендацию агента"

Событие E027 (v2): человек выбрал вариант B против рекомендованного агентом A (`overrides_recommendation: "A"`). Это не новый архитектурный кейс (укладывается в R3 ветку 1 — реплика текущему агенту), но стоит держать в уме как **отдельный тестовый/визуальный кейс**: человек не просто отвечает на decision_request, а явно идёт против рекомендации. Полезно для `04_test_plan.md` как дополнительный вариант сценария 02 (не блокирует существующий план, добавляется опционально при написании реального теста).

## Находка №10 — две числовые неувязки внутри самого датасета (не архитектурные, но проверены построчно по просьбе автора)

1. **Смета (v2, `budget`).** Верхнеуровневые `approved: 1 150 000` / `cut: 330 000` не сходятся с суммой построчных `budget.lines[].approved` (реально **1 210 000**, урезание **270 000**) — разница 60 000 ₽. Текст события E007 (перечисляет конкретные урезания: дубли -190 000, старение -60 000, закупка -20 000 = 270 000 итого) согласен с построчной суммой, не с верхнеуровневым числом.
2. **Латентность ответа (v2, E027/`metrics.longest_wait`).** Заявлено `583` минуты между E021 и E027, реально по таймстемпам — `844` минуты (или 703-704, если считать от дедлайна/начала ожидания вместо отправки запроса). Ни один разумный якорь не даёт 583.

Проверено скриптом на самом JSON, не по памяти. Обе неточности не использовались ни в одном архитектурном решении этого документа (escalation-числа взяты из отдельного самосогласованного блока `escalation_policies`, не из этих вычисляемых полей) — похоже на типичный артефакт генерации (правдоподобное число, не пересчитанное от собственных же таймстемпов датасета), не осознанный дизайн. Не исправлялось — файл пользователя.

## Что осталось без изменений

- `AgentEvent` (envelope) — не меняется по составу полей, только `stage` теперь типизирован как `str`, не `Literal`.
- Anti-echo механизм — подтверждён датасетом дословно (событие ECHO/E061: "событие... отфильтровано по автору на входе... не возвращается как человеческая").
- `correlation_id`/`payment_workflow`-канал (находка №5 грилла) — подтверждён (`correlation_key`, `channel: "payment_workflow"` в датасете — те же понятия, слегка другое имя поля, не противоречие).
- 7 сценариев валидации ТЗ §4 — все узнаваемы в `demo_cases` датасета (happy path, батчинг остаётся неподтверждённым отдельно, правка текущему/прошлому агенту, шум вне контекста, порог стоимости, недоступность ClickUp, идемпотентность) — не требуют пересмотра, датасет их иллюстрирует на новом домене.

## Практический вывод

Этот датасет — готовый источник для `sim/scenarios/costume_day.py` как **второго** demo-сценария (в дополнение к camera-based из деки), и для `docs/04_test_plan.md` как второго набора assert'ов на другом `WorkflowConfig`. Не обязательно реализовывать оба домена в MVP (`02_prototype_plan.md` не меняется по срокам) — но стоит **держать оба в голове с самого начала**, потому что именно наличие двух реальных, разных доменов и заставило найти находку №1 (стадии — конфигурация, не тип). Если бы делали только под камеру, ошибка осталась бы незамеченной до первого реального клиента с другим цехом.
