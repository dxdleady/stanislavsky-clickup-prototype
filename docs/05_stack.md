# Решение по стеку

## TL;DR

- **WebSocket не нужен нигде в прототипе.** Весь трафик — HTTP: ClickUp → нас (webhook, HTTP POST) и мы → ClickUp (REST API). Единственное место, где WebSocket теоретически мог бы всплыть — обмен Stanislavsky ↔ наш слой — зависит от того, как Stanislavsky **сам** экспортирует события, а это не описано ни в ТЗ, ни в архитектуре, ни в деке. Это открытый вопрос к владельцу Stanislavsky, не решение, которое можно принять в одностороннем порядке — см. `06_open_questions.md` №1.
- Стек: **Python 3.12 + FastAPI + Pydantic v2**, очередь — **in-process asyncio** для прототипа (см. обоснование ниже, апгрейд-путь на Redis Streams обозначен, но не нужен для сдачи).
- БД для прототипа — **не нужна** в классическом смысле: `memory.py` — это Python-словари в процессе; персистентность (переживает рестарт) добавляется только если демо должно переживать падение процесса, что ТЗ не требует (`make demo` — один прогон).

## 1. Язык и фреймворк — без вариантов, но почему именно так

Архитектура (`02_architecture.md` §1, диаграмма) уже называет `FastAPI` явно для webhook-приёмника. Это разумно продолжить на весь backend, а не только на inbound-часть:

- **FastAPI** — webhook-эндпоинт (`inbound/webhook.py`) + опционально health-check/admin эндпоинты. Pydantic-модели (`core/events.py`) переиспользуются как FastAPI request/response models без дублирования схем.
- **Pydantic v2** — контракт `AgentEvent`/`InboundEvent` уже спроектирован как pydantic-модели (`01_architecture_plan.md` §2) — валидация на границе (агент прислал мусор → падает на входе, не расползается по системе).
- **httpx** (async) — исходящие вызовы к ClickUp API из `adapters/clickup.py`.

Альтернативы (Node/TS, Go) не рассматриваются — нет сигнала, что кто-то в проекте на них завязан, а Python даёт самый быстрый путь от ТЗ до `make demo` за счёт pydantic + FastAPI, которые уже фигурируют в исходной архитектуре.

## 2. WebSocket vs webhook+REST — разбор по каждому потенциальному месту

| Место | Нужен ли WS | Почему |
|---|---|---|
| ClickUp → наш слой (комментарии, статусы, правки брифа) | **Нет** | Подтверждено прямым ресёрчем `developer.clickup.com/docs/webhooks`: классический HTTP POST на зарегистрированный URL, с HMAC-подписью (`X-Signature`) и до 5 ретраев при недоступности эндпоинта. Никакого постоянного соединения не требуется — **но** есть жёсткое требование: наш эндпоинт обязан отвечать <7 сек, иначе ClickUp деградирует/suspend'ит webhook (см. `03_clickup_requirements.md` §2.3) — это сильнее обычного "нет WS" вывода, это прямое требование к тому, что `webhook.py` не может обрабатывать событие синхронно |
| Наш слой → ClickUp (создание задач, комментариев, статусов) | **Нет** | Обычные REST-вызовы (`POST /task/{id}/comment`, `PUT` custom field и т.д.) |
| Stanislavsky-агенты → наш слой (AgentEvent) | **Не определено — открытый вопрос** | Архитектурная диаграмма показывает "Агенты → Очередь" без указания транспорта. Если Stanislavsky сам делает HTTP POST на наш эндпоинт при каждой смене стадии — WS не нужен, это симметрично webhook-паттерну ClickUp. Если же Stanislavsky ожидает, что мы **подключаемся к нему** и слушаем поток (push-модель с его стороны, например через SSE/WS/message broker) — тогда наш слой должен быть WS/SSE-клиентом. **Прототип проектируется под первый вариант (HTTP POST от Stanislavsky к нам)**, потому что он симметричен уже принятому inbound-паттерну и не требует держать сокет открытым; если это предположение неверно, меняется только `agents/*` (как Stanislavsky-клиент шлёт события), а не `core/`/`inbound/` |
| Наш слой → человек (дешборды, лента) | **Нет** | Deck прямо говорит: "всё собирается штатными средствами ClickUp... разработка UI не нужна" (`02_architecture.md` §7). Своего фронтенда с live-обновлением нет и не планируется в обозримых фазах roadmap |
| Будущее (roadmap #1, Conductor-дайджест в Chat) | **Нет** | Дайджест — это push сообщения в ClickUp Chat по расписанию/событию, не постоянное соединение |

**Вывод:** WebSocket не появляется ни в одном обязательном пути прототипа. Если он и понадобится — то только с одной стороны (Stanislavsky→нас), и то не факт. Проектировать WS "на всякий случай" не нужно — это прямо противоречит принципу ТЗ "не переписывать ядро" (WS добавил бы протокольный слой, которого сейчас架 нет ни в одном контракте).

## 3. Очередь — in-process vs внешний брокер

Требование R-надёжность: "очередь с досылкой при недоступности ClickUp", порядок доставки = порядку постановки (глобальный FIFO, см. `01_architecture_plan.md` §5.3).

**Для прототипа (`make demo`, один процесс, критерий сдачи — memory-адаптер):**
`asyncio.Queue` внутри одного процесса, с отдельной задачей (`asyncio.Task`), которая читает из очереди и вызывает `TrackerAdapter.publish()`, ретраит с backoff при ошибке. Это полностью достаточно: `make demo` — один процесс, не переживает рестарт, и не должен — ТЗ не требует персистентности очереди между запусками демо.

**Порог, после которого нужен внешний брокер (Redis Streams / RabbitMQ):** когда прототип переезжает в фазу 6 roadmap "Масштаб" (несколько бизнес-юнитов, несколько процессов/инстансов сервиса) — тогда in-process очередь не переживает рестарт процесса и не шарится между инстансами. **Явно не нужно на прототип** — но `adapters/base.py`/интерфейс очереди стоит спроектировать так, чтобы `asyncio.Queue` можно было заменить на Redis Streams-обёртку без изменения вызывающего кода (тот же принцип "адаптер", что и `TrackerAdapter`).

## 4. Хранилище состояния

Прототипу нужно где-то держать:
- state machine состояние по task_id (stage, cost, версия) — источник истины Stanislavsky по ТЗ, но для прототипа это просто in-memory dict в `memory.py`
- `processed correlation_id` для идемпотентности (аналог dedup-таблицы) — тоже в памяти для прототипа
- окна батчинга (открытые/закрытые) — в памяти, привязано к `FakeClock`/`RealClock`

**Решение: никакой БД в прототипе.** SQLite/Postgres добавляются, когда появляется требование "прототип переживает рестарт" или "несколько инстансов делят состояние" — ни того, ни другого нет в ТЗ §4 (критерий сдачи — `make demo` с зелёным прогоном, не персистентность). Явно не проектировать БД сейчас, чтобы не решать проблему, которой ещё нет.

## 5. Деплой (для фазы 6 — реальный ClickUp adapter)

Минимально: `inbound/webhook.py` должен быть доступен ClickUp по публичному HTTPS URL для регистрации webhook. Для разработки — `ngrok`/аналог (туннель к localhost). Продакшн-деплой (Docker/облако/CI) — вне рамок прототипа, ТЗ не просит; но стоит зафиксировать, что FastAPI-приложение должно уметь работать за HTTPS-прокси (уже стандартно для uvicorn+nginx/Caddy) и иметь health-check эндпоинт для мониторинга доставки очереди (сколько событий в очереди — операционная метрика, полезная уже на демо).

## 7. Auth и лимиты — подтверждено ресёрчем, фиксируем как решение

- **Personal API Token**, не OAuth2 — OAuth в ClickUp предназначен для multi-tenant приложений с произвольными внешними пользователями (интерактивный consent), у нас один известный воркспейс и известные заранее identity. Подробности и риск (Guest vs Token) — `03_clickup_requirements.md` §1, §9.
- **Rate limit подтверждён:** Business Plus (целевой тариф по деке) = 1000 req/min **per token**. При насыщенном AgentEvent (до 6 HTTP-вызовов — задача + комментарий + N custom fields, нет batch API) это даёт запас, но не бесконечный — троттлинг по `X-RateLimit-Remaining` обязателен в `clickup.py`, не опционален.
- **MCP-сервер ClickUp исключён** из архитектуры (не только "не нужен", а формально непригоден: OAuth-only + лимиты 50-300 запросов/24ч) — см. `03_clickup_requirements.md` §0.
